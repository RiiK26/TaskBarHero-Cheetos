## 2. What "Error 0" (ConnectionError) Means

* **Not an HTTP Status Code:** Standard HTTP status codes are 100–599. Status Code `0` is a synthetic client-side error code generated by Unity's **`UnityWebRequest`**.
* In Unity engine (`UnityPlayer.dll`), whenever a web request is **aborted**, **times out**, or has its **underlying TCP connection forcibly reset/closed before any HTTP headers are received**, `UnityWebRequest.responseCode` remains `0`, and `UnityWebRequest.result` is set to `Result.ConnectionError` (`2`).
* When BACKND wraps this failed `UnityWebRequest`, it sets:
  * `StatusCode: 0`
  * `ErrorCode: "ConnectionError"`
  * `Message: "No response from server"`

## 3. The 3 Root Causes of Error 0 During Box Claiming

### 3.1 Root Cause 1: Sped-Up Internal Timeout in `UnityWebRequest`
* `UnityWebRequest` runs natively inside `UnityPlayer.dll`.
* It measures request timeouts using the engine's high-resolution performance counter (`QueryPerformanceCounter`).
* In normal conditions, `UnityWebRequest.timeout` is set to **5 to 10 seconds**.
* Under speedhack acceleration:
  * At **10x speed**, a 5-second timeout window elapses in **500 ms (0.5s)** of real physical time.
  * At **20x speed**, a 5-second timeout window elapses in **250 ms (0.25s)** of real physical time.
  * At **50x speed**, a 5-second timeout window elapses in **100 ms (0.1s)** of real physical time.
* **The Reality of Internet Latency:** A real HTTPS request over the internet to BACKND's cloud servers (DNS resolution, TLS handshake, API Gateway routing, cloud function execution, SQL database update, and response delivery) physically takes **300 ms to 800 ms**.
* If the real-world network takes 400 ms:
  * At 20x speed, `UnityPlayer.dll` thinks `400ms * 20 = 8,000ms (8 seconds)` have elapsed.
  * The internal 5-second timeout fires, `UnityPlayer.dll` **aborts the request internally**, and marks it as `ConnectionError` (Code 0), even though your internet connection is 100% fine.

### 3.2 Root Cause 2: Server-Side Rate Limiting & Socket Resets
* Box opening triggers `TaskbarHero.InventoryProcessBox` via BACKND Serverless Cloud Function (`Backend.BFunc.InvokeFunction`).
* In normal gameplay, boxes are opened one by one with animations spanning 2–5 seconds.
* With cheats / speedhack active:
  * Multiple boxes are queued or opened in rapid succession (e.g. 5–10 requests in 1 second).
  * BACKND cloud function gateways have strict rate-limiting policies to prevent denial-of-service and database deadlocks.
  * When a client floods the gateway faster than allowed, the server or API gateway forcibly closes the TCP socket (`TCP RST`).
  * The client's `UnityWebRequest` encounters an abrupt socket drop and immediately throws `ConnectionError` with Status Code `0`.

### 3.3 Root Cause 3: In-Game `StageBoxRequestAbuseGuard`
TaskBarHero implements a client-side anti-spam guard specifically for stage boxes:
* **Class:** `StageBoxRequestAbuseGuard : ob<StageBoxRequestAbuseGuard>` (`TypeDefIndex: 712`)
* **Key Fields:**
  * `m_detectionIntervalSeconds` (`0x20`): Window for monitoring box request frequency.
  * `m_requestThreshold` (`0x24`): Max allowed box requests within the interval.
  * `m_blockDurationMinutes` (`0x28`): Penalty lock duration when threshold is exceeded.
  * `bgha = "StageBoxRequestAbuseGuard_BlockEndUtcTicks"`: PlayerPrefs key storing the lockout end timestamp.
* If a player spam-claims boxes faster than `m_requestThreshold` within `m_detectionIntervalSeconds`, `StageBoxRequestAbuseGuard.huh()` triggers a temporary lockout, causing queued box requests to fail.

## 4. Best Practices & Prevention

1. **Lower Speedhack Multiplier When Claiming Boxes:**
   * Dial down speedhack to **1x–3x** (or pause it) when claiming chests, opening daily rewards, or processing stage boxes.
   * This gives `UnityWebRequest` the necessary real-world milliseconds (at least 1–2 real seconds) to communicate with the cloud server without hitting the internal timeout.
2. **Avoid Rapid Spam-Clicking Box Openings:**
   * Allow each box opening animation / server callback to return before initiating the next claim to avoid triggering BACKND serverless rate limits or `StageBoxRequestAbuseGuard`.
3. **Keep `speedhack.cpp` Scoped Strictly to `UnityPlayer.dll`:**
   * Ensure `GameAssembly.dll` is never hooked so that C# background retry timers (`class qi`'s 10-second `kao()` window) do not artificially collapse.
